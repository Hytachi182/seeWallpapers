# Wallpaper engine

`DesktopWallpaperHost` owns the active wallpaper lifecycle. It creates a `WebWallpaperWindow`, waits for WebView2, injects the minimal `seeWallpaper` JavaScript API, then attaches the native window to the Windows shell `WorkerW` surface behind desktop icons.

The preview window uses that same WebView2 path without the desktop attachment, so template behaviour matches the applied wallpaper.

Win32 calls are contained in `DesktopSurface`. The implementation reuses an existing wallpaper worker, supporting both a `WorkerW` child of `Progman` in modern Explorer and the top-level worker following the icon host in classic Explorer. If neither exists, it sends the shell's worker creation messages and retries detection. It avoids workers containing the desktop icon view. Screen coordinates are converted to host client coordinates before parenting and positioning; native failures and the actual parent are checked. Failure to locate or attach to the shell is surfaced instead of silently claiming the wallpaper was applied.

Readiness is reported only after successful WebView2 navigation, settings initialization and native desktop attachment. Navigation has a 30-second timeout and is cancelled when the window closes.

The install dialog offers checkboxes for one or more displays, with app-specific numbers, resolutions and current assignments. Global clone (one independent instance per display) and span (one instance across the virtual desktop) are available under an advanced expander with readable labels and replacement consequences. The **Displays** view offers a physical layout, a scene selector per monitor, targeted installation/removal, and identification overlays that use native monitor coordinates, including negative positions. Each independent display assignment is persisted in `%LocalAppData%\seeWallpaper\configuration\wallpaper-assignments.json` with a versioned schema. Display keys are matched directly rather than by `Screen.AllScreens` ordering; a disconnected display therefore retains its record and is never silently assigned to a different monitor. Since 1.5.0, Windows monitor device interface identities are used for persistence. Legacy independent assignments require a new selection once; changed docks and ports can also require a new selection. Identity ambiguity is never guessed.

`DesktopWallpaperHost` serializes changes. It creates, navigates and attaches a replacement `WebWallpaperWindow` before closing the old instance, so a failed load does not unnecessarily interrupt another wallpaper. Targeted removal closes only that display instance. Clone and span are explicitly global replacements; applying to one display after span first exits span and gives the former span template back to each currently connected display.

The assignment service converts cloned state into independent records before persisting a local replacement or removal, preserving the other screens on restart. Removing a single screen is disabled during span. Multi-target installation is sequential, and a partial failure reports completed targets. UI controls show loading and prevent overlapping installation requests. Display-settings events are coalesced for 750 ms and reconcile active windows under the assignment lock: disconnected instances stop, recognized independent monitors restore, changed geometry reloads only the affected instance, and clone/span recompute the layout. Failures are surfaced and logged; Refresh displays retries recovery. Physical unplug/replug and scaling acceptance remains pending.

Validation on 4 October 2026: the solution builds, 16 automated tests pass (11 catalogue/storage tests and 5 application tests covering assignment transitions and native WPF screen selection). WPF renders of the gallery, display management and selection dialog are available under `build/visual-review/screen-*.png`. These renders do not prove desktop attachment or mixed-DPI identification on physical monitors.

Follow-up WorkerW validation on the same date: Windows build 26300 exposes the wallpaper worker as a child of `Progman`, which the original top-level-only search missed. With `SEEWALLPAPER_DESKTOP_TEST=1`, all 17 tests pass, including hidden native attachment and exact screen bounds on all three connected displays. A separate WPF/WebView2 smoke process successfully applied Digital Rain 3D to the primary `DISPLAY2` (3440 × 1440), waited for readiness and removed its temporary instance without saving assignments. This proves loading and attachment on that monitor; visual layering, mixed-DPI identification and hot-plug behaviour still require additional manual checks.

The desktop integration test is opt-in because ordinary CI environments may not have an interactive Explorer desktop. Run it on a Windows workstation with `$env:SEEWALLPAPER_DESKTOP_TEST = '1'; dotnet test seeWallpaper.sln`.

## Performance lifecycle

The application persists one of three profiles: `Eco` (20 FPS), `Balanced` (30 FPS), or `High` (60 FPS). The active target is delivered through `seeWallpaper.onPerformanceChanged`. Templates are expected to schedule their frames against that value. During a Windows session lock/unlock, the engine sends the documented `onPause` / `onResume` callbacks to each active wallpaper instance.

Fullscreen foreground applications and power-line status are sampled every two seconds. The Settings panel makes fullscreen and battery pauses explicit user choices. `WindowsSystemMetricsService` separately provides CPU, memory, uptime, hostname, and battery state for the future controlled system-information bridge; templates never query Windows directly.
